# レポートの構成と書き方

雛形は `../templates/report.example.md`。採点は `severity-cvss.md`。

## 書き方

- 専門家でない人にも分かる**平易な日本語**で書きます。専門用語は短い言い換えを添えます
  （例：「IDOR（他人のデータを勝手に見られる欠陥）」）。
- ASVS の要件IDは併記してよいが、必ず平易な説明とセットにします。**要件IDと文言は記憶に頼らず
  CSV から転記**します。
- 攻撃者目線の説明も平易にします。
- **秘密の値を書きません。** ハードコードされた資格情報・鍵・トークンは `file:line`・種別・影響・
  直し方だけ。値も前後の行も転記しません（再現手順に混ぜるのも同じ。`safety-policy.md` §4）。
- **対象由来のテキストを引用するときはコードフェンス内に置き、対象由来である旨を明記**します
  （共通則 §5）。

## 冒頭に必ず置くもの

- **取扱注意バナー**：「本文書は未修正の脆弱性と対象ソースの抜粋を含みます。修正が完了するまで、
  社外・公開の場に出さないでください。」
- **`tools.semgrep.required: false` で semgrep を実行しなかった場合は、その旨をここに第一級で明記**
  （「静的スキャン未実行。以下は LLM による精読のみに基づく」）。読んだ人が、何をせずに出した結果かを
  最初に分かること。

## 共通の構成（各回・統合の両方）

1. **対象プロファイル／実施したスキャン設定**：言語/FW/アプリ種別/テスト基盤、選定した semgrep の
   `--config`・`--exclude` と選定理由、**実際に使ったモデル**、攻撃マップの規模（エントリポイント数等）。
2. **サマリー（冒頭・平易）**：
   - 深刻度ごとの件数（Critical / High / Medium / Low）。
   - 見つかった主な問題を1件1行で平易に列挙（例：「ログインしていなくても他人の注文履歴が見える」）。
   - アプリ全体のリスクを2〜3文で一言まとめ。
3. **指摘の詳細（深刻度の高い順）**：各指摘について
   - 平易な見出し ＋ ASVS要件ID（CSVから転記）
   - 判定（問題あり / 一部問題 / 該当なし / 要確認）と深刻度（Critical/High/Medium/Low）
   - 場所：ファイル名と行番号
   - わかりやすい説明：何が起きるのか、なぜ危険か
   - 深刻度の根拠：CVSS v4.0 ベクター文字列＋スコア（参考値）＋平易な一言、開発/本番差
   - 再現手順：詳しくない人でも追える手順。できるだけブラウザ操作（どこを開く・クリック・URLのどこを
     書き換える・画面に何が出れば問題か）。コマンドが要るときはコピペできる短い curl 等にし「ここを
     こう変える」と注記。前提条件（ログインの要否、必要アカウント数）も明記。**アプリ種別が Web 以外
     なら、その種別に合った様式**（CLI ならコマンド、ライブラリなら呼び出し例 等）。
     **手順は文章として書くだけで、自分では実行しません**（`safety-policy.md` §2）。
   - 直し方：該当ファイルでどこをどう変えるかのレベルで。使うべき関数・チェックを入れる場所・検証の
     追加位置を短く示す。設定/依存更新で直る場合はその手順も。
   - 追加すべきテストケース：**対象の既存テスト基盤に合わせる**。各テストは「目的／入力（操作や
     リクエスト）／期待される結果（アサーション）」を平易に、可能なら短いコード骨子を添える。
4. **該当なしの章**：探した上で無いことを根拠付きで一言（単なる「該当なし」で流さない）。
5. **最終まとめ**：「確実に問題」と「要確認」を分けた一覧表。

## 統合レポート(04)で追加する要素

- 各指摘の出現回数（3/3・2/3・1/3）と信頼度【高/中/低】。
- 3回のばらつき一覧（各回件数・主要指摘の出現状況・各回が見落とした本物・各回の誤り）。
- 攻撃マップ由来のカバレッジ要約（確認/総数、観点別）。
- 件数は欠陥単位で重複排除＋影響インスタンス数を併記。
- タイトル等で「統合版」である旨を明示。

## 依存（SCA）の書き方

ロックファイルから依存とバージョンを列挙するところまでは事実として書けますが、**バージョン→CVE の
対応づけは、オフラインの根拠が無い限りすべて「要確認」**とします（`safety-policy.md` §2）。記憶で
CVE 番号や「既知の脆弱性あり」と断定しないこと——共通則 §7（推測と事実の分離）の具体例です。
