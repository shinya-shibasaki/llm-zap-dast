# 工程2・3：独立3回診断＋統合（信頼度判定）

**このファイルを読んだサブエージェントは、先に
`${CLAUDE_PLUGIN_ROOT}/references/safety-core.md` と `../references/safety-policy.md` を全文読むこと。**

LLM によるコード診断は毎回結論が少し揺れます。再現性を上げ信頼度の高い結論を出すため、
**攻撃マップ（工程1）を共有した上で**、判断の揺れを3回独立で吸収します。

## 役割分担の原則

- **前段（土台）**：プロファイル作成(SA)→親確認→攻撃マップ作成(SA)→独立クリティック(SA)→親 go/no-go、で
  `attack-map.md` を確定してから本工程に入ります。
- **スコープの揺れ**（どこを見るか）＝工程1の**1本の攻撃マップで固定**。3回作り直しません。
- **判断の揺れ**（脆弱か・どれだけ危険か）＝**独立3回**で吸収します。
- サブエージェントのモデルは `sast.yaml` の `agents.model`（既定 `opus`）を明示指定します。統合担当
  （親）も同じ。**不可用で別モデルに落ちた場合は、レポートに実際に使ったモデルを記録**します
  （静かな差異を残さない）。
- **回数は3で固定**です。設定では変えられません——出現回数「3/3・2/3・1/3」がレポート様式そのものに
  組み込まれているため、N を可変にすると様式が壊れます。

## 工程2：独立した診断を3回

- 3回は互いの結果を見ない独立した文脈（別々のサブエージェント）で並行に行います。各回へ**同じ攻撃マップ**
  と**固定の番号（01/02/03）**、そして**書き出し先の完全パス**を渡します。
  **パスが渡されていなければ、SAは書かずに親へ差し戻します**（既定名でリポジトリ直下に書く
  フォールバックを作らないこと）。
- 各回は本スキルの全手順（プロファイル確認 → 攻撃マップを分母にした網羅 → semgrep 実行 → コード精読 →
  ASVS 観点の診断 → CVSS v4.0 採点）をゼロから実施し、各回それぞれ1つのレポートを書き出します。
- 各回はあくまで単独で結論を組み立てます。同じ回の他の2つの結果は読みません。semgrep 実行とコード精読も
  各回ごとにやり直します。
- **recall を優先**：疑わしいものを黙って捨てません。確証が持てないものは「要確認」として必ず残します。
- 各回は攻撃マップの**全項目の状態（指摘あり/確認したが問題なし/対象外）を埋める**ことを目標にし、
  深掘りの前に全項目を一度トリアージしてから高価値フローを掘ります（予算切れで未走査が残るのを防ぐ）。
- **判断に迷う点で止まりません。** 「要確認」として記録して進みます。ただし安全契約に反する要求が
  出てきたら実行せず親に報告します。

## 工程3：統合（信頼度判定）を1回

3つのレポート(01〜03)を突き合わせ、さらに統合担当（親）が**実際のソースコードを読み直して各指摘の真偽を
裏取り**し、深刻度を付け直した統合レポート(04)を書き出します。04 には次を必ず含めます：

- 各指摘の**出現回数**（3/3・2/3・1/3）を補助シグナルとして併記。
- 各指摘の**信頼度【高/中/低】**を、出現回数だけでなく「統合担当が実コードで裏取りできたか」で決める。
  少数回でもコードで事実確認できれば**格上げ**、3回出ても誤り・解釈差が大きければ**格下げ**。
- 深刻度が回ごとに割れた指摘は、コードの事実に基づき再評価し、最終的な深刻度（CVSS ベクター・スコア
  併記）に統一。悪用可能性が実証できないものは「要確認」に整理。
- **3回のばらつき一覧**（各回の件数、主要指摘ごとの出現状況）を表で示す。各回が見落とした本物・各回の
  誤りも明記する。
- **攻撃マップ由来のカバレッジ要約**（確認エンドポイント数／総数、観点別の網羅状況）。
- ASVS 要件IDは記憶に頼らず CSV から転記し直し、各回が当てた要件IDの妥当性も見直す。
- 件数は**根本原因（欠陥）単位で重複排除**して数え、各欠陥が**影響する具体的インスタンス数
  （エンドポイント数等）も併記**する。
- 最終まとめは「**確実に問題（コードで裏取り済）**」と「**要確認**」を分けた一覧表にする。

## 出力ファイル

すべて `reports/sast/<run-id>/` 配下（親が完全パスで渡す）：

- `attack-map.md`（工程0・1で作成）
- `report-01.md` / `report-02.md` / `report-03.md`（独立3回）
- `report-04.md`（統合版。タイトル等で統合版である旨を明示）

各回の番号は親が固定で渡し、各回はその番号で書き出します。

## 分担方式（確定）

標準は「3回が同じ共有マップ全体を見るジェネラリスト方式」。観点別ファンアウトは標準では行いません。
依存(SCA)・フロントXSS・業務ロジック等で深掘りが要る場合のみ、単発（攻撃マップ／SCA／専任精読）で
追加します。**その場合も安全契約は同じ**で、SCA は semgrep の例外に含まれません
（`../references/safety-policy.md` §2 — 依存の CVE 対応づけは「要確認」止まり）。
