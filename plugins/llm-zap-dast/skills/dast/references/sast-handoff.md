# SAST 成果物の取り込み（`sast.enabled: true`）

**このファイルを読んだサブエージェントは、先に
`${CLAUDE_PLUGIN_ROOT}/references/safety-core.md` と `../references/safety-policy.md` を全文読むこと。**
（親が安全契約ブロックを渡し忘れていても届くよう、経路を二重にしています。）

このファイルは、`/llm-zap-dast:sast` が過去に出した成果物を DAST の工程1〜2 へ**どう変換するか**の
権威です。**安全の側は書きません** — 読んでよいファイル、SAST 由来を仮説と根拠に限る規律、停止と
続行の線引きは `../references/safety-policy.md`「SAST 成果物の取り込み」が権威です。

## 何のためにやるか

SAST は**静的には解けない問いを名指しで残します**。実測した成果物では、要確認14件のうち10件が
「稼働環境で確かめる」と明記され、その筆頭が「JWT の署名検証関数が正しく呼ばれているか」でした
（依存ライブラリの実体が `.gitignore` 済みで読めないため、**SAST を何回回しても解けない**）。
有効・無効なトークンを1回ずつ送れば決着します。これが連携の中心的な価値で、副次的に攻撃面の
分母が広がります。

## 前提：置換ではなく補強

**工程1（自前のソース解析）は縮約しません。** attack-map は工程1 の結果に**足す**もので、
診断対象マップは両者の和集合です。理由は安全側にあります——工程1 を置換すると、SAST 側の解析範囲や
除外設定の縮退が、そのまま DAST の分母の縮退になり、**体裁は正常なまま攻撃面が欠けたレポート**が
出ます（`safety-policy.md` の停止表の注記）。

## 読む単位

`sast.report` が指す run ディレクトリの **`attack-map.md`** と **`report-04.md`** の2本だけです
（allowlist の根拠は `safety-policy.md` ルール10）。`latest` は `reports/sast/latest.json` を
直接読み、**工程0 で1回だけ解決して run-id を固定**します（工程6・工程7 で再解決しない。
その間に SAST が回れば別 run を掴みます）。

## 委譲の形（直列・2体）

工程2 で、**順番に**2体走らせます。並列にして親が突き合わせる形は採りません——実測で
突合キーが揃わず、親が両方の全文を抱えることになるからです。

1. **子1（攻撃面）** — `attack-map.md` を読み、`target-map.md` を**新規に書く**
2. **子2（指摘）** — できた `target-map.md` と `report-04.md` を読み、**同じファイルに追記・更新する**

子2 が子1 の出力を直接見るので、行キーの語彙を発明する必要がありません。親は**検算だけ**を行い、
どちらの全文も読みません。

# 子1 — `attack-map.md` → 診断対象マップ

## 抽出する節

| 節 | 何に使うか |
|---|---|
| 対象プロファイル（基本情報・バックエンド・フロントエンド・依存/設定） | **工程0 の対象照合が使う材料**として、読み取った値をそのまま親へ返す。**停止するかどうかを子が決めない**（契約4条） |
| §2.1 finale 等の自動生成 REST の認可マトリクス | 行（下記の展開規則） |
| §3 独自 REST / 画面ルート（E 番号） | 行 |
| §1 ミドルウェア（M 番号）のうち**パスを持つもの** | 行。配信面（`/ftp`・`/encryptionkeys`・`/support/logs` 等）は E 行に現れないが直接到達できる |
| §7.1 画面ルート（C 番号）のうち**入力を持つもの** | 行。反射型 XSS の突合先はここ（ハッシュルート `#/...` を含む） |
| §5.1 WebSocket（W 番号）・§5.2 起動時処理/ジョブ（J 番号） | 行。**別表に分離しない**（下記） |
| §8 危険シンク（S / X 番号） | 「注目点・想定脆弱性」列の材料。**S 行の「到達経路」列が E 番号を持つので、これが突合の第一キー**（子2 が使う） |
| §9.2 信頼レベル集計（path × method） | 「認証」「認可の実態」列。**この節が認可の権威** |
| §9.3 / §11 | 「未確認事項」列。§11 には作成者自身の不確実性の自認が入っている |

**節番号ではなく ID 体系（M / E / W / J / D / C / S / X / N）と件数節を契約として扱ってください。**
attack-map は毎回書き下ろされる散文で、節構成は run ごとに揺れます（実測では `§8.8b` のような
不規則もありました）。節番号をキーにした抽出は、外れたときに例外にならず「0件」で静かに縮退します。

## 自動生成 REST の展開規則

自動生成された CRUD（モデル × メソッドのマトリクス）は、**到達できるセルだけを行に展開**し、
**恒常的に拒否されるセル（`denyAll` 相当）は1行に集約**します。同一モデルの拒否セルを個別行に
しても診断できることが増えないためです。集約行にも行を1つ与え、優先度は低にします
（**優先度は順序であって範囲ではない**ので、低でも完了条件からは外れません）。

集約したセルは「該当なし（理由：恒常拒否）」ではなく、**拒否の実装が本当に効くかは1回確かめる**
対象です。実測した対象では拒否が乱数 secret に依存していました——**「拒否と書いてあるから安全」は
SAST 由来の記述であって実測ではありません**。

## 射程外を分離しない

WebSocket・起動時処理・ジョブは「HTTP DAST の射程外」に見えますが、**別表へ落とさず行として
載せます**。理由は2つです。

- **事実として射程外とは限りません。** WebSocket ライブラリは polling トランスポートを持つことが多く、
  その場合イベントは HTTP で送れて ZAP の履歴にも載ります。ジョブも、HTTP 起点の操作が成功した
  副作用として発火する経路（second-order）があります。実測した対象では、チャレンジ成立を契機に
  **外部へ POST する webhook ジョブ**が存在しました（8C の材料なので「外部送信」列に第一級で載せる）。
- **分母から外して完了条件を満たすのは、`scenario-testing.md` が禁じている操作の鏡像です。**
  終端の語彙は既にあります——HTTP 経由の入力点が無いものは**「該当なし（理由）」**、プローブ能力が
  無いものは**「未実施（理由）」**。1行で終わります。

## 列の写像

| attack-map | → | 診断対象マップの列 |
|---|---|---|
| `ルート`（`POST /rest/user/login` の形） | → | URL / エンドポイント ＋ メソッド |
| `入力源` | → | 入力（データ形式は attack-map に無いので DAST 側で補完。明示されるのは multipart 等だけ） |
| `到達するシンク` ＋ §8 の分類 | → | 注目点 / 想定脆弱性 |
| `認証・認可` ＋ §9.2 の分類 | → | 認証 ／ **認可の実態** ／ ロール |
| `file:line` | → | file:line（登録／実装） |
| §8.6 SSRF・外部通信 ＋ 依存 | → | 外部送信（**宛先の解決値は工程1 が読む** — 下記） |
| §9.3 / §11 | → | 未確認事項 |
| — | → | 優先度（下記の規則） |
| — | → | 根拠（出自ラベル `[H]` ＋ attack-map の ID） |

## 「認可の実態」列 — 潰してはいけない4状態

信頼レベルを「認証：要／不要」の2値に潰すと、**SAST が最も苦労して確定させた情報が消えます**。
次の4つは必ず別の値として残してください。

| 状態 | なぜ2値に潰せないか |
|---|---|
| **所有者 ID を差し込むだけのミドルウェア**（`appendUserId` 等） | 「認証＝要」と書くと**誤り**。所有権もロールも検証していない |
| **恒常拒否**（`denyAll` 等） | 認証要否の軸に無い第3状態。しかも実装が乱数依存で「安全とは限らない」 |
| **ハンドラ内の自前チェック** | 後付けの認可ミドルウェアが無く、実質要認証。ミドルウェア一覧からは見えない |
| **ロール判定はするが拒否しない** | 認証不要だが応答が分岐する |

## 外部送信列は工程1 が埋める

**8C（サンドボックス外への副作用）の宛先判定は「実測」できません。** パスワードリセットが実際に
メールを出すかを実測する行為は、そのまま送信＝8C 違反です。**送る前に静的に決めるしかありません。**

attack-map は**追跡ファイル内の設定に書かれた宛先**は持ちますが、`.env` 由来の宛先は持ちません
（SAST は `.env` を読まないため）。したがって **`.env.example` / `docker-compose*` / 環境変数由来の
宛先設定を読むのは工程1 の仕事**です（`source-analysis.md`）。attack-map からはシンクの所在だけを
受け取り、宛先が不明なら「不明」と書いて工程6 では発火させません。

## 検算（親が行う）

子1 の出力は、attack-map 自身が持つ件数で照合できます——§0 の件数要約と §9.2 の分母、
`routes/*` の対応づけ件数、ID の連番。ただし**検算材料そのものが間違っていることがあります**
（実測では §9.2 の内訳の1つが範囲と個数で食い違っていました）。

なので子1 には「**合った／合わない**」ではなく「**どこがどう合わなかったか**」を返させ、
**数を合わせるために項目を落としたり作ったりさせない**でください（契約7条）。親は差分を
`run.log` に残し、必要なら該当節だけを読んで裁定します。

# 子2 — `report-04.md` → 診断対象マップへの追記

## 読む節（§4 と §9 だけでは足りない）

**節番号は目安であって鍵ではありません**（子1 側と同じ規律）。見出しの文言で探し、**見つからなければ
「その節が見つからなかった」と親へ差し戻します** — 黙って0件にしない。とくに件数の節を取り違えると
**検算そのものが静かに空振りします**。

| 節（目安） | 見出しの手がかり | なぜ要るか |
|---|---|---|
| **§0**（何を見ずに／せずに出したか） | 「読まなかった」「せずに出した」「第一級」 | **縮退の判定材料はここにしかない**。「どのルールパックが取得できず、どの言語に静的スキャンが未適用か」「静的スキャナが1件も検出しなかった領域」。後者は **DAST が最も補える領域の指定**そのもの |
| **§2.1**（件数） | 「件数」「サマリー」 | **唯一の完全な検算源**（深刻度別の件数と ID 範囲） |
| **§4**（指摘の詳細） | 「指摘の詳細」 | 仮説と根拠の本体 |
| **§5**（各回の誤りと統合で行った訂正） | 「誤り」「訂正」「棄却」 | **攻撃マップの仮説が棄却されている場合がある**。下記 |
| **§8**（カバレッジ要約）のうち**走査しきれなかった範囲** | 「カバレッジ」「走査しきれなかった」 | SAST が見ていない範囲＝工程4 で DAST が独自に当たるべき範囲 |
| **§9**（要確認） | 「要確認」 | 静的に決着しなかったもの＝**DAST の仕事そのもの** |

**§5 を読ませないと、SAST が精読して否定した仮説が診断対象マップに生き残ります。** 実測した
成果物では、攻撃マップがパストラバーサルのシンクとして登録した3件を統合担当が棄却し、
「**攻撃マップ側の該当エントリも『否定済み』と読み替えてください**」と書いていました。
ところが attack-map 本文はそのシンクを載せたままです。**否定は反映しますが、行は消しません** —
「SAST が静的に否定済み／DAST で追認する」対象として残します（静的な否定を動的に反証するのは
DAST の中核価値です）。

## 書式の罠

指摘は**同じ文書の中で3つの書式で書かれます**——見出し、太字行、表の行。見出しだけを機械的に
拾うと**半分以下しか取れません**。さらに：

- **節見出しの深刻度と、集計表の深刻度が一致しないことがあります**（バンドは低いが修正優先度が
  高い指摘を、上位の節の末尾に置く形）。**深刻度は §2.1 の集計から取り、節見出しから推測しない。**
- **別掲の指摘は連番の外にあります**（実測ではスマートコントラクト層の6件が別 ID 体系）。
  「§4 の指摘＝連番の全部」という前提を置かないでください。
- 表形式で書かれた指摘には**再現手順や URL の欄がありません**。全件を同じ形で出せという指示は
  そこで必ず埋まりません。「欄が無い」を「該当なし」と書かせてください。
- ID の文字列は文書内で**複数回出現します**（本体・訂正記録・最終まとめ）。件数を数えるときは
  **指摘本体の節に限って**数えます。

## 何を写し、何を写さないか

| 写す | 写さない |
|---|---|
| 仮説（確認したい命題を1文で） | **再現手順の操作列**（「(1) …して (2) …する」） |
| 根拠（file:line ＋ コードの事実） | 直し方・修正案 |
| **ペイロードの実例**（根拠の一部） | CVSS ベクターとスコア |
| 期待される安全な挙動 | 追加テストケース |
| SAST が既に否定したか（§5） | ASVS 要件の全文 |
| 深刻度（§2.1 由来） | |

**ペイロードは残します。** 実測では、指摘の説明文そのものにペイロード例が含まれており
（「メール欄に `' OR 1=1;--` のような文字列を入れると条件が常に真になり」）、これは
「なぜそう判定したか」の中核です。**消すと根拠が壊れます。** 工程6 は対象の文脈から自分で
ペイロードを組み立てますが、SAST の例は根拠として読んで構いません。

**手順は写さないが、手順の中に現れるエンドポイント文字列は抽出してよい。** 実測では、
**指摘の1/5 は URL が再現手順や追加テストケースの欄にしか現れず**、「場所」欄は file:line しか
持ちませんでした。手順ごと捨てると突合先を失います。

**「直し方」の転記は特に避けてください。** `report-format.md` の修正案は「**DAST が確認した事実に
対する**修正案」であって、別 run の静的推論の転記ではありません。証拠の分離が壊れます。

## 突合（多段。URL 一本槍にしない）

実測では、**URL の文字列が完全一致するのは突合可能な指摘の2割弱**でした。揺れはクエリ付き、
`<id>` と `:id`、具体値とパラメータ、末尾スラッシュ、メソッドの有無、ハッシュルート、
グロブ（1件が複数行に展開）の7種。

しかも**外れるより誤って当たる方が危険です。** 実測では指摘の1件が**実装と食い違う URL**を
書いており（存在しないパラメータ付きのパス）、正規化してファジー一致させると**隣接する別の
エンドポイントに誤着地**します。

上から順に試し、**最初に当たった段で確定**してください。

1. **§8 のシンク経由** — 指摘の file:line が §8 の S 行と一致し、その S 行の「到達経路」列が
   E 番号を持つなら、それが答え。**正規化不要で最も確実**
2. **file:line 直接** — 行番号まで一致させる。**ファイル名だけの一致は使わない**（中枢ファイルが
   ほぼ全行にヒットして偽陽性になる）。なお「登録行」と「シンク行」は別物で、指摘は主に後者を、
   攻撃面の行は両方を持つ
3. **URL 正規化** — 上記の7種の揺れを吸収する。**メソッドが違えば別の行**
4. **どれも当たらない → 「未突合」として第一級で記録**。曖昧一致で無理に当てない

## 行に貼れない指摘の受け皿

実測では、**指摘の4割前後が診断対象マップの1行に落ちません**。2種類あります。

- **非エンドポイント** — 暗号方式（ハッシュアルゴリズム）、依存、CI/CD 設定、コンテナ設定、
  別言語の静的資産。対応する URL が存在しない
- **横断的** — トークン偽造（要認証の全セルに掛かる）、CSRF 対策の欠如、Cookie 属性、
  全許可 CORS、セキュリティヘッダ不在。1行に紐づけられない

これらは**診断対象マップの「横断・非エンドポイント指摘」節**に入れます（下記の出力構造）。
別ファイルに逃がさないのは、工程6 のカバレッジ行列と同じ場所にあった方が落ちにくいからです。
横断的な指摘は、**該当する行の「注目点」列に ID だけを併記**して相互参照を張ります。

## 検算（親が行う）

§2.1 の件数表（深刻度別の件数と ID 範囲、別掲、要確認）で照合します。**ID は指摘本体の節に
限って数える**こと。子1 と同じく、合わない場合は差し戻しであって、辻褄合わせではありません。

# 出力の構造

診断対象マップ（`target-map.md`）を**3構成**にします。ファイルは1つです——同じ仮説が2つの
ファイルに載ると、片方だけ更新されて食い違います。

```
target-map.md
├─ 1. エンドポイントの表      … 1行1エンドポイント。根拠列には SAST の指摘 ID だけを書く
├─ 2. SAST 指摘の根拠（本文）  … ID ごとに、仮説・根拠・file:line・否定済みか・深刻度
└─ 3. 横断・非エンドポイント指摘 … 行に貼れないもの
```

表のセルに本文を詰め込まないでください。実測では**1つのエンドポイントに指摘が5件付く**ケースが
あり、表が壊れます。**表は ID で参照し、本文は2番目の節**に置きます。工程6 は表で対象を選び、
ID を辿って本文を読みます。工程7 の突合表は2番目と3番目の節が分母です。

冒頭には**この分母の限界**を書きます（§0 由来の未適用スキャン・未走査範囲、`run_id`、
古さ・縮退の有無）。SAST 成果物の内容をここへ全部コピーはしません——**run_id を書けば原本が
読めます**。書くのは「この DAST が何を欠いた分母で走ったか」の要約だけです。

# 優先度

**優先度は「どれから先に撃つか」の順序にだけ使い、「撃つかどうか」には使いません**
（`scenario-testing.md` の完了条件は全エントリに掛かります）。この一点で、SAST 由来のデータが
診断範囲を縮める経路が塞がります。

決め方：

1. **SAST の指摘があれば、その深刻度**（§2.1 由来）
2. 無ければ **`§9.2` の認可の実態**（未認証で到達でき、後付けの認可も自前チェックも無いものが上）

**シンクの分類は優先度に使いません。** 実測した attack-map の §8 は「ティア別」と題されていますが
**深刻度の順位ではなく分類**（SQL / コード実行 / ファイル / SSRF …）で、表に深刻度列がありません。
それ以上に、**危険シンクを持たない行に High 以上の指摘が多数ぶら下がります** — 認可の欠落・IDOR・
業務ロジック・マスアサインメントは、定義上シンクを持たないからです。実測した成果物自身が
「静的スキャナはこの領域を1件も検出せず、重大な指摘の大半は精読による補完だった」と書いています。

**SAST が「否定」した項目の優先度は下げてよいが、分母からは外しません。** 静的に「到達不可能に
見える」を実際に叩いて反証するのは DAST の仕事です。

# 出自ラベル

診断対象マップの凡例に3つ目を足します。

- `[S]` — **この run** でソースを読んで確認した
- `[I]` — 推測
- `[H]` — **伝聞**。SAST 由来（別 run の別エージェントがソースで確認した事実）。**ID を併記する**

`[H]` は `scenarios.md` と `report.md` まで生存させます。DAST 自身は SAST の文書を読んでいないので、
`[H]` を `[S]` に混ぜると**未検証の主張が自分の実測に化けます**（`report-format.md` の証拠分離）。

# 親の役割

親は**どちらの子の入力も全文読みません**。行うのは次だけです。

1. 子1・子2 の起動（安全契約ブロックを逐語で貼り、貼ったことを `run.log` に記録）
2. 検算（上記2箇所）と、合わなかった点の差し戻し
3. `execution-summary.json` に `sast: {run_id, path}`、`report.md` §5 に使用した SAST run の1行
4. 子の書いた成果物を `redaction.md` の書き出し後検証に掛ける（SAST 側の宣言を前提にしない）
