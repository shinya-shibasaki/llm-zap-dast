# 工程7 — 結果整理とレポート形式

ZAPアラート＋シナリオ結果を `findings.md` に分析し、次に最終 `report.md` を生成する
（テンプレート `templates/report.example.md`）。

## 証拠の分離（必須）

各検出を2軸で分類し、ラベルを付ける：

- **事実の出所**：ツール検出の事実／HTTPで確認できた事実／**この run** でソースを確認した事実／
  **伝聞（別 run の SAST がソースで確認した事実＝`[H]`。指摘IDを併記）**／LLMの推測。
  `[H]` を「ソースで確認できた事実」に混ぜない — **DAST 自身は SAST の文書を読んでおらず**
  （読むのは工程2 の子）、混ぜると未検証の主張が自分の実測に化ける。`[H]` の項目を DAST が実際に
  再現できたなら、その時点で「HTTPで確認できた事実」へ**昇格**させ、根拠として指摘IDを残す。
- **確度**：再現できた／再現できなかった／誤検知の可能性／人間の確認が必要。

根拠のない断定をしない。LLMの推測はそのようにラベル付けし、確認済みの脆弱性として提示しない。

**「人間の確認が必要（要人間）」を出す各項目には、監査のため次を必ず記録する**（`scenario-testing.md`
の要人間の発行規律）：**(a) 試行した検証**（手持ちの Playwright/ZAP/curl で何を試したか）、
**(b) ブロッカー種別**（次の4種のいずれか：8C要／8B要／8Aだが `destructive:false`／自動化不能な人間判断。
**能力欠如はここに含めない**——それは「要人間」ではなく「未実施（理由）」）、**(c) 次の一手**。
**(b) が4種でなければそれは要人間ではない**——`scenario-testing.md` の決定木に戻し、安全かつフラグの
範囲で確認できるなら**その一手を実行する**（段1）。撃てない理由が能力欠如や運用上の回避なら
**「未実施（理由）」として記録する**（段3）。

## report.md — 必須セクション（15）

1. 診断概要
2. 対象情報（URL、ホスト、スコープ、除外パス）
3. 実行日時
4. 使用したツール（ZAPバージョン、Playwright、スクリプト）
5. 実行した診断工程 — **スキップした工程とその理由を含む**
6. 探索範囲（カバレッジ）
7. 未到達範囲
8. 検出結果一覧
9. 再現確認結果
10. 証拠（マスク済み）
11. リスク説明
12. 修正案
13. 未確認事項
14. 診断上の制約（グレーボックス、認証は「できなければ停止」、キーなし＝ローカル限定 など）
15. 免責事項

**認証付きDAST（`authentication.enabled`）を行った場合**、5〜7 に加えて次を明記する
（状態は 成功 / 失敗 / 未確定 / 未実施 で。詳細は `authentication.md`）：採用した認証方式・認証設定
結果・認証確認結果・認証後探索結果・認証付きActive Scan結果・認証状態を維持できたか・**未認証と
認証後のカバレッジ差**・LLM追加診断結果・実施できなかった認証工程・認証後診断で未確認となった範囲。
**認証は「できなければ停止」で、任意アプリでの認証成功は保証しない**旨を制約（14）に記す。
**アカウント構成**（単一／同一ロール2／異ロール／3）と、それにより**実施できた認可クラス
（水平IDOR・垂直権限昇格など）／できなかったクラス**も明記する。

**SAST 連携（`sast.enabled: true`）を行った場合**、8（検出結果一覧）に続けて
**「SAST 指摘 × DAST 検証」の突合表**を置く（セクションは増やさない）。

- **分母は診断対象マップの「SAST 指摘の根拠」節と「横断・非エンドポイント指摘」節の全件。**
  URL に紐づかない指摘（暗号方式・依存・CI/CD・コンテナ・別言語の静的資産）と横断的な指摘
  （トークン偽造・CSRF・Cookie 属性・CORS・セキュリティヘッダ）は診断対象マップの行にならないが、
  **この表からは落とさない**。実測ではこれが指摘全体の4割前後を占めた。
- **終端の語彙は工程6 と同じ**：確認／否定／要人間（理由）／未実施（理由）／該当なし（理由）。
  加えて**未突合**（どのエントリにも貼れなかった）を**判定列の値**として持つ（突合先列ではない。
  両方に書くと集計が二重計上になる）。
- **無言の打ち切り禁止は突合表にも掛かる。** 空欄で濁さない。
- **DAST が再現できなかったことを、SAST 指摘の格下げ根拠にしない。** 「再現できなかった」と
  「誤検知の可能性」は別の値であり（上記の確度軸）、前者で終端する。SAST 側が実コードで裏取り
  済みの指摘を、DAST の1回の未到達で消さない。
- 5（実行した診断工程）に、**使用した SAST run-id とパス**を1行で書く。SAST 側の縮退内容は
  原本（`report-04.md` §0）に書かれているので**転記しない** — run-id があれば辿れる。

**破壊・可用性の設定**（制約 14）：`scan.destructive`（対象内部の破壊。既定ON・使い捨てローカル
前提）と `scan.availability_impact`（DoS相当。既定OFF）の有効/無効を記す。destructive 有効時は
**対象内部を不可逆に変更した項目**を証拠（10）に残す。外部への副作用（8C）は行っていない旨も記す。

**工程6カバレッジ（無言の打ち切り禁止）**：セクション6（探索範囲）に、診断対象マップの**全エントリ**の
うち**工程6でプローブしたもの／未実施のもの（理由付き）**を明記し、`scenarios.md` の
「対象×クラス→判定」カバレッジ行列を根拠として参照する。**未実施が多い場合はその事実を埋もれさせない**
（時間・トークンの都合で撃てなかった分も理由とともに前面化する）。安全停止・フラグOFF・破壊順序による
未実施は、失敗ではなく正当な終端として区別して記す。行列には **`attempted_tool` 列**（各セルで実際に
試した検証手段。LLM が記入）を持たせ、「要人間／否定」なのに何を試したかが追える状態にする（これは
LLM の自己申告＝プロンプト規律層であり、機械的な DoD 違反チェックは設けない）。

## 免責事項の内容（セクション15）

次を明記する：これはLLM支援型のグレーボックスDASTであり、完全な手動ペンテストの代替ではない；
結果には誤検知/検知漏れが含まれ得る；許可されたホストのみを診断した；検出結果は対応前に人間の
確認を要する；対象は**自分が所有する使い捨てのローカル脆弱アプリ**であり、`scan.destructive` 有効時は
対象内部を不可逆に変更する検証を含む（サンドボックス外への副作用は行わない）。

## 併せて出力する

- `execution-summary.json` — 機械可読：run-id、実行 vs スキップした工程＋理由、タイムスタンプ/
  所要時間、ツールの利用可否、Active Scanを実行したか、**`scan.destructive`/`scan.availability_impact`
  の有効・実際に破壊的検証を実行したか**、**認証アカウント構成（単一/同一ロール2/異ロール/3）**、
  **工程6カバレッジ（対象マップの総エントリ数・プローブ済み数・未実施数）**、
  マスク状況、**ZAPをスキルが自動起動したか（起動した場合は後始末で停止したか）**、
  **`sast.enabled: true` なら `sast: {run_id, path}`**（`report: latest` は時点で解決されるため、
  `dast.yaml` からはどの SAST run を読んだか復元できない。逆に縮退や古さは run_id から辿れるので
  記録しない＝事実だけ残し、導出できる判断は残さない）。
- レポート中の証拠はマスク済みであること（`redaction.md` 参照）。
