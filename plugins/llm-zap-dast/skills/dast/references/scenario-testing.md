# 工程4・6 — カバレッジ補完とシナリオ診断

## 工程4 — カバレッジ分析＋Playwright補完

1. ソース抽出URL（工程1）と、ZAPが実際に到達したURL（工程3）を**比較**する。未到達を次のいずれ
   かに分類：
   - ログイン必須／JavaScript操作必須／特定の画面遷移が必要／特定のデータが必要／管理者権限が
     必要／URLは存在するが未使用／APIが画面から直接呼ばれない／クローラーでは到達困難。
   `reports/dast/<run-id>/coverage-analysis.md` に保存。
2. Playwright（または利用可能なブラウザ操作）で、未到達画面へ**ZAP Proxy経由で**遷移し、ZAPに
   記録させる（`zap-integration.md` 参照）。ブラウザ操作が無い → スキップ（fail-soft）、理由を記録。

   **Playwright の有無は工程0の `check_environment.py`（`playwright` チェック）で判定済み**で、
   結果には**使用すべきインタプリタのパス**が含まれる。それをそのまま使うこと。自前で
   `import playwright` を試して判断しない — 対象リポジトリに `.venv` があると `pip install --user`
   で入れた Playwright は venv からは見えず、**実際には入っているのに「無い」と誤判定**する
   （venv は既定で `~/.local` の site-packages を隠すため）。この工程は fail-soft なので、
   誤判定はエラーにならず**静かに工程4が飛ぶ**。

許可される操作：ログイン、メニュー操作、フォーム送信、JS生成画面、複数ステップ遷移、権限別画面
確認。

**工程4（カバレッジ目的）で巻き込み発火させない操作**：データ一括削除、ユーザー削除、パスワード変更
等の破壊的操作。工程4はナビゲーションが目的で、破壊はデータを失いカバレッジを狭める。**意図的な
破壊検証は工程6で `scan.destructive` に従って行う**（工程4では `scan.destructive` が有効でも回避）。
**工程4・6の両方で常に禁止（8C）**：外部メール送信、課金、外部サービス登録、実在内部インフラへの
副作用など、`allowed_hosts`／サンドボックスの外に出る操作（`references/safety-policy.md`）。

## 工程6 — シナリオベース診断（能動探索）

この工程では、LLMがソース解析（工程1）とZAP履歴（工程3）から仮説を立て、対象ごとにペイロード／
リクエストを組み立てて送信し、応答を観察して調整・再送し、脆弱性を確認または否定する。工程1〜4の
結果を入力とし、結果は工程7のレポートに渡す。

ZAP Active Scan（工程5）は汎用の注入を広く自動で撃つ。本工程はそれと独立に動き、次を担う。

1. ZAPが到達できない注入点（認証後・多段・JS依存・隠しパラメータ・JSON/GraphQL本文）への送信。
2. ソース文脈（テンプレートエンジン、DB、反射位置）に合わせたペイロードの作成。
3. ロジック・認可・IDOR・業務フローの推論。

対象はロジック系だけでなく、XSS・SQLi・テンプレート注入・SSRF などの注入系も含む。
`scan.scenario_tests: true`（既定）のとき実行する。Active Scan が無効でもこの工程は実行する。

### 安全制約

安全制約は「送信してよい範囲」と「行ってはならない操作」を定める。制約の内側であれば、ペイロードを
能動的に組み立てて送信してよい。破壊の扱いは3軸（`references/safety-policy.md` ルール8）に分かれる。

- スコープ：`allowed_hosts` のホストのみに送信する。`exclude.paths` を除外する。スコープ外へは
  送信しない。
- **8A 対象内部の破壊（`scan.destructive`・既定ON・使い捨てローカル対象）**：対象アプリ内部の
  不可逆な状態変更（削除・更新・パスワード変更・実際に権限が上がる Mass Assignment・実 `DELETE`
  など）を**確認まで踏み込んで実行してよい**。「検出止まり／要人間」に留める必要はない。ただし
  **何を不可逆に変えたか**を記録し、破壊が後続テストのカバレッジを奪う点に注意する（順序を工夫し、
  破壊系は後回しにする）。`scan.destructive: false` のときは**検出止まり**（悪用・状態
  変更は要人間、良性の一意マーカーや読み取りを優先）。
- **8C サンドボックス外への副作用（常に禁止・破壊フラグでも解禁されない）**：外部メール送信、課金、
  外部サービス登録、実在の内部インフラへの SSRF、`allowed_hosts` の外へ出る操作。これらは使い捨て性で
  正当化できないため、`scan.destructive` の有無に関わらず**実行しない**（必要なら要人間）。
- **8B 可用性・DoS相当（`scan.availability_impact`・既定OFF）**：重い time-based 探索・大量リクエスト・
  可用性を損なう負荷は既定で行わない（run 途中で対象が落ちるとカバレッジを失う）。レート確認は上限を
  決めた小さなバーストに限る（これは 8B ではない）。`scan.availability_impact: true` のときのみ、
  可用性に影響し得る検証を対象内部に対して行ってよい。

### 認証後プローブの追加制約（`authentication.enabled` 時・`references/authentication.md`）

- **実施できる範囲はアカウント構成（`authentication.users`）で決まる**：
  - **同一ロール2アカウント（例 user1／user2）**：水平IDOR・水平権限昇格・「別人のトークン」系が可能。
    A として B のリソース識別子/トークンを用い、他人のデータに触れられるか確認する。
  - **異なるロール（低権限＋管理者）**：垂直権限昇格の拒否確認（低権限→管理者ルート→403期待）が明確化。
    管理者側は「正解の姿」のベースラインとして使う。
  - **3アカウント（同一ロール2＋管理者）**：水平＋垂直の両方。
  - **単一アカウント**：水平系は構造的に不可能なので**「単一アカウントのため未実施」と記録**する。
    単一でも可能なのは：垂直権限昇格の拒否確認・認証回避・強制ブラウズ・**同一ユーザーの**セッション/
    JWT改ざん・CSRF・自分へのMass Assignment・隠しパラメータ・メソッド改ざん。
- **どのプローブをどの User で実行したかを常に明示**する。**forced-user は Context 単位で1人しか
  固定できない**ため、アカウントを跨ぐ検証（A→B）は forced-user の張り替えではなく `--user-id` を
  明示した scan/送信で行う。各アカウントの応答が**そのアカウント自身の身元**を反映しているか
  （別人のセッションに化けていないか）を差分で確認する。
- **ログアウトを誘発するプローブ（セッション無効化・ログアウト後・別トークン・`alg:none`）の実行中は
  自動再認証（forced-user）をOFF**にし、終了後に意図的に張り直す。放置すると再ログイン連打で
  ロックアウト＋`max_attempts` 枯渇 → **以降が静かに匿名化**し、結果が誤帰属になる。
- 認証失効の可能性がある区間の結果は「認証済み」と断定しない（未確定として記録）。

### 能動探索ループ

診断対象マップの優先度順に、各ターゲットへ次を適用する。

1. 仮説：ソース（認可の位置、入力の扱い等）とZAP履歴から、想定される欠陥とその根拠を挙げる。
2. プローブ作成：エンドポイント固有のパラメータ・認証・content-type に合わせ、まず**最小の証拠で
   済むプローブ**（良性マーカー・読み取り・差分）を組み立てる。汎用の使い回しではなく文脈に合わせる。
   確認に状態変更が要る場合は、`scan.destructive` が有効なら対象内部の変更まで踏み込む（8C=外部
   副作用は常に回避、8B=可用性は `scan.availability_impact` のときのみ）。
3. 送信：curl / Playwright / ZAP のリクエスト送信APIで送る（ZAP Proxy経由で履歴に残す）。正常系の
   ベースラインも取得し、差分で判断できるようにする。
4. 観察：ステータス・本文・ヘッダ・タイミング・反射・差分を確認する。
5. 調整・再送：応答に応じてペイロードを修正し、必要なだけ再送する。
6. 結論：確認／否定／要人間に分け、証拠（マスク済み）を記録する。

### クラス別プローブ

いずれも allowed_hosts 限定・8C（外部副作用）禁止。**`scan.destructive`（既定ON）が有効なら、
対象アプリ内部の状態変更まで踏み込んで確認してよい**（削除・更新・実際の権限昇格など）。
`scan.destructive: false` のときは各項目の「検出止まり／要人間」に留める。8B（DoS相当）は
`scan.availability_impact`（既定OFF）が有効なときのみ。

- IDOR / オブジェクト認可：**同一ロールの2アカウント**で識別子を入れ替え、他人のリソースに触れられるか
  確認する。読み取り（GET）に加え、destructive 有効なら他人リソースへの更新/削除の可否まで確認する。
  アカウントは `--user-id` 明示で切り替える。
- 垂直権限昇格 / 機能認可：管理者ルート／アクションを低権限セッション／トークンで再送し、拒否
  されるか確認する。destructive 有効なら状態変更を伴う管理操作もそのまま実行して受理可否を確認する
  （無効時は読み取り版で確認し、無ければ要人間）。
- 認証回避 / セッション：Cookie/JWT の改ざん（`alg:none`、署名なし、期限切れ、別人のもの）、
  無認証リクエスト、保護ルートへの強制ブラウズを試す。
- CSRF：トークンの有無と検証を確認する。トークンを外した／改ざんしたリクエストが受理されるかを確認する。
  destructive 有効なら破壊的アクションでの受理確認まで行ってよい（無効時は良性アクションで確認し、
  破壊でしか確認できないものは要人間）。
- 反射/DOM/格納 XSS：良性の一意マーカー（例：`zdast<乱数>`）で反射とエスケープ文脈を確認し、
  **「反射のみ／要人間」で止めず、自分の管理下のヘッドレスブラウザ（Playwright）で良性・副作用なしの
  マーカーを実行・観測して「確認」へ格上げする**（`window.__zdast=1` を立てる／無害なDOMノードを足す
  だけ。ネットワーク送信・外部遷移・サブリソース取得は伴わせない＝8C回避）。**発火を確認したらそこで
  止め、動作する完成ペイロードへは格上げしない**（証拠は増えず影響範囲だけ増える）。DOM XSS は応答本文の
  反射では判定できずブラウザ実行が唯一の確認手段（ZAP の DOM-XSS 自動被覆＝要 Firefox と補完関係で、
  工程6は ZAP 未到達＝認証後/多段/JS依存を担う）。**格納型は保存＝書き込み＝8A** なので `scan.destructive`
  に従う（既定ON＝保存してレンダー画面で実行観測、`false` は検出止まり／要人間）。**保存内容はその生存
  期間ずっと良性・副作用なし**であること（後で実ブラウザで開いても無害）。何を書いたかは破壊記帳へ記録し、
  破壊系は後回し。能力の一次情報は工程0（Playwright 自己検証＝`playwright`／ZAP DOM-XSS＝`browser_firefox`）。
  **第三者/被害者のブラウザでの実行・情報の外部送出は常に禁止（8C）。**
- SQLi / NoSQLi：boolean差分（`' OR '1'='1` と `' AND '1'='2` の応答差）や単一引用符による
  エラー誘発で検出する。destructive 有効なら stacked query や `UPDATE/DELETE` で対象内部の
  変更可否まで確認してよい（`DROP` 等でスキーマを壊すと以降が診断不能になるため順序に注意）。
  **重い time-based（DoS相当）は 8B 扱いで既定オフ**（`scan.availability_impact` 時のみ）。
- コマンド/テンプレート注入（**SSTi を含む**）：`${7*7}` / `{{7*7}}` → 49 のような良性の評価確認で
  検出する（テンプレートエンジンのサーバーサイド評価＝SSTi はここで扱う）。destructive
  有効でも、**対象ホスト外や基盤に影響するコマンド（8C）は送らない**。対象コンテナ内部で完結する
  破壊は destructive の範囲。
- XML / XXE：XMLを受理する入力（アップロード・API本文・SOAP/B2B旧IF等）に、外部実体で**対象内部の
  ローカルファイルを読み出し、応答に反射させる in-band 確認**を行う。**外部DTD取得・データの外部送出
  （out-of-band）は SSRF＝8C にあたるため常に禁止**（SSRF クラスと同じ扱い。宛先は対象内部/制御
  マーカーに限る）。**重い実体展開（billion laughs 等）は DoS 相当＝8B** で `scan.availability_impact`
  のときのみ。良性の一意マーカーで「外部実体が解決・反射されるか」を確認し、実データの大量抽出は行わない。
- ファイルアップロード：拡張子/MIME/サイズ検証の回避、Zip Slip、パストラバーサルを確認する。
  **意図しないパスへの書き込み（Zip Slip／`../` によるファイル配置）は状態変更＝8A** で、
  `scan.destructive` 有効時のみ実際の書き込みまで確認し（無効時は検出止まり／要人間）、**何を書いた/
  上書きしたかを記録**する（重要ファイル上書きは後続カバレッジを壊すため順序注意）。パストラバーサルの
  **読み取り**は非破壊で可。アップロード後に格納される内容の実行/反射は XSS クラスへ接続。**外部への
  到達・実在インフラへの副作用は 8C で禁止**。
- 逆シリアライズ（ノート・独立クラスにしない）：信頼できない入力が脱シリアライズされる箇所は**ソースで
  検出**し、良性マーカーで「脱シリアライズが実際に起きるか」までを確認する。**RCE の完全実証は
  out-of-band コールバック（8C）や重い/副作用不明な実行に寄るため原則「要人間」**。構造化データ爆弾
  （YAML/JSON 爆弾等）は DoS 相当＝8B で既定オフ。
- オープンリダイレクト：リダイレクト先を**良性の制御マーカーURL（対象内部/ループバック）**にし、
  30x/Location を確認する（これは自己検証で8Cでない＝「要人間」にしない）。到達確認は制御マーカーで
  足りる。**被害者を実在の外部先へ実際に遷移させることだけが 8C** で、これは行わない。
- SSRF：取得系パラメータを良性のループバック／制御マーカーに向けて反応を確認する。**実在の内部
  インフラや外部サービスを叩かない（8C・破壊フラグでも禁止）**。
- Mass Assignment：書き込み系に想定外フィールド（`role`、`is_admin` 等）を加えて受理されるか
  確認する。destructive 有効なら実際に権限が上がるところまで確認してよい（テストアカウントで行う）。
- HTTPメソッド改ざん：`PUT/DELETE/PATCH/OPTIONS` 等を試す。destructive 有効なら実リソースへの
  `DELETE` も可（破壊がカバレッジを奪う点に注意し順序を工夫）。無効時はテストリソースか要人間。
- 隠し/未文書パラメータ：ソースに存在しUIに現れないパラメータを送り、挙動の変化を確認する。
- レート制限：上限を決めた小さなバーストで制限の有無を確認する。全面的な負荷（DoS相当）は 8B 扱い。

### 工程6の完了条件とカバレッジ（無言の打ち切り禁止）

工程6には**検証可能な完了条件**を置く。高価値プローブを数本撃っただけで自己判断で切り上げ、診断対象
マップの残りを未実施のまま終えることを防ぐためである。fail-soft の「スキップは黙って行わず log する」
思想（`SKILL.md`・`safety-policy.md`）を、この工程の**プローブ網羅**にも適用する。

- **完了条件（DoD）**：診断対象マップ（工程2）の**優先度 高／中**の各エントリについて、そのエントリに
  **該当する（仮説上関係する）プローブクラス**を検討し、「実行したプローブ＋判定、または未実施なら理由」が
  揃うまで工程6を完了としない。**該当しないクラスまで総当たりする必要はない**——文脈適合・仮説駆動の
  原則（本節冒頭「まず最小の証拠で済むプローブ」）を崩さない。非該当クラスは「該当なし（理由）」を
  正当な終端とする（水増しプローブで行列を埋めない）。
- **カバレッジ行列**：`scenarios.md` に「**対象（マップのエントリ）× プローブクラス → 判定**」の行列を
  必ず残す。セルの値は **{確認 / 否定 / 要人間 / 未実施（理由） / 該当なし（理由）}** のいずれか。
  「未実施」を**第一級の判定**として扱い、空欄で濁さない。判定語彙は工程7の確度区分
  （再現できた／できなかった／誤検知の可能性／要人間）に揃える。
- **「要人間」の発行規律（全クラス共通）：要人間は例外であって既定ではない。** 付けてよいのは次の
  いずれかのときだけ——(i) 確認に **8C** 侵害が必要、(ii) 確認に **8B**（`availability_impact:false`）が
  必要、(iii) 確認に**状態変更（8A）が要るが `scan.destructive:false`**、(iv) 本質的に自動化不能な
  人間判断（業務ロジックの正誤等）。**能力が無いだけなら「要人間」ではなく「未実施（理由：能力欠如＋
  工程0引用）」にする。** 要人間を付ける前に、**安全かつフラグの範囲で可能な最も確実な検証を試し、その
  試行を記録する**（手持ちの Playwright/ZAP/curl で確認できる項目を「ブラウザ／人間が要る」を理由に
  格下げしない。自己検証は8Cではない＝`references/safety-policy.md`）。ただし available でも、その確認が
  **安全/フラグ制約**（ロックアウト・ログアウト誘発・可用性・forced-user・`destructive:false`）に触れる
  なら、無理に実行せず「未実施（安全/フラグ理由）」で終端する。
- **無言の打ち切り禁止**：時間・長さ・トークンの都合で全該当セルを撃ち切れない場合も、**未実施の
  エントリ／クラスとその理由を明示**する（黙って終えない）。1コンテキストで長すぎる場合は、対象を
  落とさないために**プローブクラス単位で分割・並列化してよい**（分割は網羅のための手段であって、
  打ち切りの口実にしない）。
- **DoD は安全停止に劣後する**：`authentication.enabled` の停止条件（`safety-policy.md`・工程2.5）や
  スコープ・破壊フラグの制約に抵触する場合は、DoD より安全が優先。停止・回避したセルは
  「未実施（安全停止／フラグOFF／破壊順序による）」として記録するのであって、**行列を埋めるために
  8B（可用性）や `scan.destructive` を勝手に有効化しない**。撃てないことが正しい設定は、そのまま
  「未実施（理由）」で終端する。

### 各シナリオに記録する

- シナリオID、対象機能、想定される脆弱性、根拠
- 前提条件、操作手順、組み立てたペイロード／リクエスト（機微はマスク）、試した反復
- 期待される安全な挙動と脆弱時の挙動
- 実行可否、実行結果、証拠、追加確認事項（要人間の残作業を含む）

### その他の制約

- 証拠は保存前にマスクする（`redaction.md` 参照）。
- 確認済み（再現した）と、疑い／要人間確認を分ける。根拠のない断定はしない。

`reports/dast/<run-id>/scenarios.md` に保存（テンプレート
`templates/scenario-list.example.md`）。レポートへ進む前にチェックポイント。
